# 从零上手：Java 8 + Spring Boot + GitHub Actions

这条教程带你从「本地跑通」走到「合并即上线」，中间会**故意弄红一次流水线**，让你看清它是怎么救你的。

预计用时 60–90 分钟。每一步都有"你应该看到什么"，对不上就停下。

---

## 0. 你机器上现在有什么

| 工具 | 状态 |
|---|---|
| JDK | Corretto **1.8.0_512**（arm64）✅ 就是你要的 1.8 |
| Maven | 3.9.9，装在 `_tools/`，用 `./dev-mvn.sh` 调起 |
| Docker | 29.9.2 ✅ |
| git | 2.50.1 ✅ |
| gh CLI | 没装（第 3 步可选装） |

项目就在 `spring-ci-cd-demo/`，已经能跑。

---

## 1. 第一步：本地跑通（5 分钟）

```bash
cd spring-ci-cd-demo

# 编译 + 跑测试
./dev-mvn.sh verify
```

**你应该看到**：

```
[INFO] Tests run: 7, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

`target/app.jar` 就是产物。跑起来：

```bash
"$(/usr/libexec/java_home -v 1.8)/bin/java" -jar target/app.jar
```

另开一个终端：

```bash
curl "http://localhost:8080/api/hello?name=CI"
# {"message":"Hello, CI!","version":"dev"}
curl http://localhost:8080/api/health
# {"status":"UP"}
```

> `version` 是 `dev`，因为版本号由环境变量 `APP_VERSION` 注入，本地没给。流水线里会注入提交号。

**这一步的意义**：CI 里跑的就是同一条 `mvn verify`。本地不过，线上一定不过。

---

## 2. 第二步：初始化仓库

```bash
cd spring-ci-cd-demo
git init -b main
git add .
git commit -m "feat: 初始 Spring Boot 项目 + CI 流水线"
```

先确认流水线文件在：

```bash
ls .github/workflows/     # ci.yml
```

> 目录必须是 `.github/workflows/`，少一层、多一层都不会被 GitHub 识别。这是新手第一个坑。

---

## 3. 第三步：推到 GitHub

### 方式 A：网页建仓 + 命令行推

1. 打开 https://github.com/new
2. 仓库名填 `spring-ci-cd-demo`，**Public**（免费跑 Actions；私有仓库会消耗额度）
3. 不要勾 README / .gitignore（本地已有）
4. 然后：

```bash
git remote add origin https://github.com/<你的用户名>/spring-ci-cd-demo.git
git push -u origin main
```

### 方式 B：gh CLI（更省事）

```bash
brew install gh
gh auth login          # 选 GitHub.com → HTTPS → 浏览器授权
gh repo create spring-ci-cd-demo --public --source=. --remote=origin --push
```

**注意**：仓库名如果带大写字母，ghcr.io 会拒绝推送镜像。流手里已经做了转小写处理，但你看到 403 时先想这里。

---

## 4. 第四步：看它跑起来

推到 main 的瞬间，Actions 就被触发了。

1. 打开仓库页 → **Actions** 标签
2. 左边选 `CI`，右边点最新一次运行
3. 你会看到三个方块依次点亮：

```
① 构建与测试  →  ② 构建镜像  →  ③ 部署到生产
```

**预期耗时**（第一次，无缓存）：约 1 分 40 秒。第二次开始有 Maven 缓存，约 40 秒。

点开 `① 构建与测试`，展开 `编译并运行测试`，你能看到和本地一模一样的 Maven 输出——包括那 7 个测试。**runner 是一台干净的 Ubuntu 虚拟机，每次都是全新的**，这是理解 CI 的关键。

---

## 5. 第五步：逐段读懂 ci.yml

打开 [`.github/workflows/ci.yml`](.github/workflows/ci.yml)，对照着看：

| 段 | 作用 | 一句话 |
|---|---|---|
| `on:` | 触发条件 | push 到 main、提 PR、打 tag、手点 |
| `permissions:` | 令牌权限 | 推镜像需要 `packages: write` |
| `concurrency:` | 并发控制 | 连推两次，取消旧的，别浪费额度 |
| `env:` | 全局变量 | `JAVA_VERSION: '8'` |
| `jobs.build` | 阶段一 | 编译、测试、留档 jar |
| `needs: build` | 依赖 | 镜像必须在构建成功后才开始 |
| `if: github.event_name != 'pull_request'` | 条件 | PR 不推镜像、不部署 |
| `actions/setup-java` + `cache: maven` | 装 JDK | 顺带缓存 `~/.m2` |
| `upload-artifact` | 产物 | 把 jar 和测试报告存成可下载文件 |
| `environment: production` | 人工门禁 | 配了审批人后，这里会停下来等人 |

### 三个容易忽略的细节

1. **`if: always()`** 挂在"上传测试报告"上：否则测试一失败，报告就不会上传，你反而看不到失败原因。
2. **`needs` 是串行，不是并行**：`build` → `image` → `deploy` 是一条链，任何一环红，后面都不跑。
3. **`GITHUB_TOKEN` 是自动注入的**，不用你配 Secret，但 PR 来自 fork 时它只有只读权限——这也是 PR 阶段不推镜像的原因之一。

## 6. 练习一：故意让它红 ⭐ 最重要的一步

目的：让你相信"流水线真的能拦住错误"，而不是走个过场。

打开 `src/test/java/com/example/demo/GreetingServiceTest.java`，把：

```java
assertEquals("Hello, CI!", service.greet("CI"));
```

改成：

```java
assertEquals("Hello, CI!!", service.greet("CI"));   // 多一个感叹号
```

然后：

```bash
./dev-mvn.sh verify          # 本地先红一次
git add -A && git commit -m "test: 故意改坏断言"
git push
```

**你应该看到**：Actions 里 `①` 变红，`②` 和 `③` 直接跳过（灰色），整条链停住。

进去看日志：

```
[ERROR] GreetingServiceTest.greetsByName:17 expected: <Hello, CI!!> but was: <Hello, CI!>
```

再去 run 页面底部 **Artifacts** 下载 `test-reports`，解压后 `surefire-reports/*.txt` 里就是同样的错误。**这就是"留档"的意义：失败时证据还在。**

现在改回来，再 push 一次，看着它变绿。

---

## 7. 练习二：走一遍 PR 流程

```bash
git checkout -b feature/add-greeting-prefix
# 随便改点东西，比如给 greet 加个前缀参数
git commit -am "feat: 支持自定义前缀"
git push -u origin feature/add-greeting-prefix
```

在 GitHub 上点 **Compare & pull request** 提 PR。

**关键观察**：这次只有 `① 构建与测试` 会跑，`②`、`③` 不会——因为 `if: github.event_name != 'pull_request'` 把它们挡住了。

这是刻意的设计：**PR 阶段只验证，不产生副作用**（不推镜像、不碰生产）。合并到 main 之后，完整链路才会跑。

---

## 8. 练习三：装上人工门禁

这一步把视频里讲的"闸门"变成真的：

1. 仓库 → **Settings** → 左侧 **Environments** → **New environment**
2. 名字填 `production`（必须和 yml 里的 `name: production` 一致）
3. 勾选 **Required reviewers**，把自己加进去
4. 保存

再 push 一次代码到 main。你会看到：

- `①` 绿 → `②` 绿 → `③` 显示 **Waiting for approval**
- 点 **Review deployments** → **Approve and deploy** → 才继续

**这就是「持续交付」和「持续部署」的分界线**：流程全自动，但最后一步留给人。

想改成"持续部署"（合并即上线），把 environment 里的审批人去掉就行。

## 9. 制品和镜像都去哪了

| 东西 | 位置 | 下载方式 |
|---|---|---|
| jar | 每次 run 页面底部 **Artifacts** → `app-jar` | 网页下载 |
| 测试报告 | 同上 → `test-reports` | 网页下载 |
| 镜像 | 仓库右侧 **Packages**，或 `ghcr.io/<user>/spring-ci-cd-demo` | `docker pull` |

拉下来试试：

```bash
docker pull ghcr.io/<你的用户名>/spring-ci-cd-demo:latest
docker run --rm -p 8080:8080 ghcr.io/<你的用户名>/spring-ci-cd-demo:latest
curl localhost:8080/api/hello
```

镜像里的 `version` 是那次的提交号——**同一个 tag 永远对应同一份字节**，这就是视频里说的"不可变制品"。

## 9.5 本地也构建一次镜像（可选，但强烈建议）

流水线里 `②` 那步跑的就是这条命令。先在本地确认 Dockerfile 没问题，别等 push 了才发现：

```bash
# 前提：先 ./dev-mvn.sh package 产出 target/app.jar
docker build -t spring-cicd-demo:local --build-arg APP_VERSION=local .
docker run --rm -p 18081:8080 spring-cicd-demo:local
curl "localhost:18081/api/hello?name=Container"
# {"message":"Hello, Container!","version":"local"}
```

`version` 是 `local` 而不是 `dev`，说明 `--build-arg` → `ENV` → 配置项 这条链是通的。流水线里换成 `${{ github.sha }}`，镜子里就带上了提交号。

**关于体积**：这个镜像 442MB，因为 `eclipse-temurin:8-jre` 本身就这么大。想瘦身可以换 `8-jre-alpine`（约 100MB），或上 jlink 裁剪运行时——都属于进阶，先跑通再优化。

清理：

```bash
docker rmi spring-cicd-demo:local
```

## 10. 发一个版本

```bash
git tag v1.0.0
git push origin v1.0.0
```

tag 也会触发流水线（`tags: [ 'v*' ]`），而且 `deploy` 会跑。

**进阶想法**：给 tag 单独写一个 `release.yml`，用 `softprops/action-gh-release` 把 jar 挂到 GitHub Release 上。这是留给你的作业。

## 11. 一定会踩的坑

| 现象 | 原因 | 解法 |
|---|---|---|
| `class file version 61.0` 报错 | 用了 Spring Boot 3 / Java 17 编译 | Java 8 只能用 Boot **2.7.x** |
| runner 上 `java -version` 不是 8 | 没写 `setup-java` 或版本写错 | 显式 `java-version: '8'` |
| `./mvnw: Permission denied` | wrapper 脚本没执行位 | `chmod +x mvnw` |
| 缓存不生效，每次都很慢 | key 变了 | `cache: maven` 会根据 pom 内容算 key，改依赖就会重建 |
| 推 ghcr 报 403 | 仓库名有大写 / 无 `packages: write` | 转小写 + 加权限 |
| fork 来的 PR 挂了，日志说没权限 | fork 的 token 只读 | 正常现象，PR 阶段别做写操作 |
| 中文乱码 | runner 默认编码 | 加 `-Dfile.encoding=UTF-8` |
| 本地能跑、CI 挂 | 跑了没提交的文件 | `git status` 看漏了什么，或加 `.gitignore` |

---

## 12. 学会了之后往哪走

按收益排序：

1. **矩阵构建**：`strategy.matrix.java: [8, 11, 17]`，一次验证多版本兼容
2. **依赖漏洞扫描**：`dependency-check` 或 GitHub 自带的 Dependabot
3. **部署到 K8s**：把 `deploy` 里的占位换成 `kubectl set image`，配合 `kubectl rollout undo` 回滚
4. **蓝绿 / 金丝雀**：`deploy` 里先切 10% 流量看指标，再全量
5. **缓存分层**：把 Maven 依赖和构建输出分开缓存
